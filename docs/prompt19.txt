Security flow:

Request
→ JWT authentication middleware
→ authenticated user added to request
→ RBAC confirms `VISITOR`
→ controller reads authenticated user ID

→ safe profile response returned

Important:
Use only the authenticated ID from the verified JWT.

Do not read user ownership from:

- query parameters
- URL parameters
- request body
- frontend-provided userId

Do not create an endpoint such as:

Fetch the authenticated User and related VisitorProfile using a safe `select`.

- zip

PHASE 4 — PATCH VISITOR PROFILE
==================================================

Create:

PATCH /api/visitor/profile

Accepted fields:

{
  "phone": "9876543210",
  "address": "Nedumangad",
  "state": "Kerala",
  "zip": "695541"
}

All fields should be optional for PATCH, but at least one valid field must be provided.

Use Zod validation.

Validation rules:

phone:
- optional
- trimmed string
- exactly 10 digits

address:
- optional
- trimmed string
- reasonable maximum length, such as 255
- allow an empty string only if the current project allows clearing optional values

state:
- optional
- trimmed string
- reasonable maximum length, such as 100

zip:
- optional
- trimmed string
- exactly 6 digits when provided

Reject:

- empty body
- userId
- role
- password
- passwordHash
- email
- name
- profile image
- any unsupported field

Prefer a strict Zod object or equivalent behavior so unsupported fields are rejected rather than silently trusted.

PATCH security flow:

Frontend sends edited data
→ JWT authentication
→ VISITOR RBAC
→ Zod validation
→ controller reads `req.user.id`
→ service confirms profile exists
→ Prisma updates only that VisitorProfile
→ safe updated profile response returned

Do not allow a visitor to update another visitor.
