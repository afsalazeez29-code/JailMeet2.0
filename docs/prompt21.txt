STEP 3 — BACKEND: PRISONER CREATE PAROLE REQUEST
============================================================

Endpoint: POST /api/prisoner/parole

Zod validation (adapt field names to Step 1's confirmed schema):
- reason: string, trimmed, min 10 chars, max 1000 chars, required
- requestedDate: ISO datetime string, optional (ONLY include this field if Step 1 confirmed it exists in the schema)
- Use .strict() so any other field (status, prisonerId, officerId, role, userId) causes a 400 validation error

Business rules enforced in the service layer (not just Zod):
1. Only PRISONER role may call this endpoint (RBAC middleware)
2. Prisoner identity comes ONLY from the verified JWT (req.user.id) — resolve to the PrisonerProfile server-side, never trust a client-supplied prisonerId
3. status is ALWAYS set to PENDING by the backend — never accept it from the request body
4. officerId is never set at creation time
5. Duplicate-pending rule: a prisoner cannot have more than one active PENDING parole request at a time. If one already exists, return 409 "A pending parole request already exists"

Expected success response:
{
  "success": true,
  "message": "Parole request submitted successfully",
  "data": {
    "id": "...",
    "reason": "...",
    "status": "PENDING",
    "replyMessage": null,
    "createdAt": "..."
  }
}
