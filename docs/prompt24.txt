STEP 3 — BACKEND SERVICE: changePassword
============================================================

Implement changePassword(userId, input) in auth.service.ts:

1. Fetch the User by userId (from JWT — req.user.id, never from the request body) — select only id, password (hash field), and the account-status field
2. If user not found → 404 "User not found"
3. If account-status field indicates inactive → 403 "Account is inactive" (protects against an already-issued token surviving deactivation)
4. bcrypt.compare(currentPassword, user.password) — if false → 400 "Current password is incorrect". Do not reveal any other detail.
5. bcrypt.compare(newPassword, user.password) — if true (new password same as current) → 400 "New password must be different from the current password"
6. bcrypt.hash(newPassword, <the same salt rounds config confirmed in Step 1>) — reuse the exact existing hashing configuration/helper, do not hard-code a new pattern
7. Prisma update: User.password = hashedPassword (only this field, nothing else touched)
8. Return void/safe confirmation — never return the password or the hash

The service must never trust userId, role, or any identity field from the request body — identity comes exclusively from the authenticated req.user.id.

STEP 4 — CONTROLLER + ROUTE
============================================================

Controller (auth.controller.ts) — keep it small, no bcrypt or Prisma logic here:
```
export async function changePassword(req, res, next) {
  try {
    await authService.changePassword(req.user.id, req.body);
    return res.status(200).json({
      success: true,
      message: "Password changed successfully",
      data: null
    });
  } catch (error) {
    next(error);
  }
}
```

Route (auth.routes.ts) — add to the existing auth router:
```
router.patch(
  "/change-password",
  authenticate,
  validate(changePasswordSchema),
  changePassword
);
```

Final endpoint: PATCH /api/auth/change-password

No role-specific RBAC middleware is needed — all authenticated roles may use this endpoint for their own account. Authentication (valid JWT) is still required.

============================================================
IMPORTANT KNOWN LIMITATION (report this explicitly, do not silently work around it)
============================================================

Since the JWT system is stateless (no token versioning, no session table), changing a password does NOT automatically invalidate previously issued access tokens on other devices/browsers until they naturally expire. The chosen mitigation for this first version is: clear the current browser's token and force a fresh login. This does not revoke tokens elsewhere. A stronger design (tokenVersion field, passwordChangedAt check in auth middleware, refresh-token revocation) is explicitly OUT OF SCOPE for this task — do not implement it, just note it as a known follow-up in your final report.

============================================================
SECURITY RULES (apply throughout, verify explicitly in final report)
============================================================

- JWT identifies the user — userId is never accepted from the frontend body
- All roles may change ONLY their own password
- Current password must be verified via bcrypt.compare before any change is applied
- New password must be validated (length, and reused strength rules if applicable)
- New password must differ from the current password
- bcrypt hashes the new password using the same configuration as registration
- Password and password hash are never returned in any API response
- Unknown fields are rejected (.strict())
- Passwords are never logged, never stored in localStorage, never placed in URLs
- Inactive users are rejected even with a still-valid token
